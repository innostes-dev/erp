| Path | What it is |
| --- | --- |
| `apps/` | Deployable applications. `api-server` and `web-app` are the two **engines**; `landing` is the website and docs. Apps can depend on packages, never on other apps. |
| `kernel/` | The first **plug-in**: shared foundation for all ERP modules, with a `backend/` (Python) and a `frontend/` (React) part. See [Kernel](/docs/architecture/kernel). |
| `packages/` | Shared, reusable code. Can be published to npm. |
| `nx.json` | Nx settings: plugins, task defaults and release config. |
| `pnpm-workspace.yaml` | Which folders are workspace packages (`apps/*`, `packages/*`, `kernel/*`) and which install scripts may run. |
| `tsconfig.base.json` | TypeScript settings shared by every project. |
| `tsconfig.json` | Project references, kept up to date by `nx sync`. |

## Naming

- Every project has an npm name in the `@innostes/` scope, e.g. `@innostes/web-app`.
- Nx uses a short name for tasks, e.g. `pnpm nx build web-app`. It's set in each `package.json`
  under `"nx": { "name": "..." }`, or in `project.json`.

## How projects depend on each other

Workspace packages are linked with the `workspace:*` protocol:

```json title="apps/landing/package.json"
{
  "dependencies": {
    "@innostes/ui": "workspace:*"
  }
}
```

Nx reads these links to build the dependency graph. When you run `pnpm nx build landing`, Nx builds
`@innostes/ui` first. Run `pnpm nx graph` to see the whole graph.

## What's not in git

Build output (`dist/`, `.next/`), `node_modules/`, the Nx cache and the API's `.venv/` are ignored,
as are `.env` files (only `.env.example` is committed) and `kernel/backend/var/` (runtime files such as
the generated setup token). `.dockerignore` keeps the same files out of Docker images.
AI assistant folders (`.claude/`, `.cursor/`, `AGENTS.md`, …) are also ignored, so each developer
can keep their own setup. `pnpm-lock.yaml` **is** committed.
