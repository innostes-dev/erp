The kernel is the first plug-in. It has two kinds of code:

- **`core`**: infrastructure with **no tables**: settings, database, security, the module contract,
  and base classes for schemas and services.
- **Platform features**: features every ERP module relies on, each with its own tables and API.
  Today: **tenancy** and **setup** (first-run installation, see [First-run Setup](/docs/architecture/setup)).
  Next: identity (users), access (roles and permissions), audit.

- **No build step.** The package is used from source; Vite compiles it as part of web-app.
- **Compare errors with constants**, never with raw numbers or strings: `error.status === HttpStatus.CONFLICT`,
  `error.code === SetupErrorCode.SETUP_REQUIRED`.
- **Each feature gets a frontend folder**, mirroring its backend one: `api.ts` (calls), `types.ts` (matching
  the backend schemas), and its components and pages.

## Feature layout

Every feature has the same shape, so you always know where to look:

| Folder / file | Holds | Base class |
| --- | --- | --- |
| `models/` | SQLAlchemy tables, only the feature's own columns | `BaseModel` |
| `schemas/` | Request and response bodies | `BaseSchema`, `AuditReadSchema` |
| `services/` | Business logic | `BaseService[Model]` |
| `router.py` | HTTP endpoints | `APIRouter` |
| `__init__.py` | Public exports and the `BaseModule` subclass | `BaseModule` |

Other code imports a feature only through its package: `from kernel.tenancy import Tenant`.

## Common columns

Every table inherits `BaseModel` and gets these columns automatically, in this order:

| Column | Type | Set by |
| --- | --- | --- |
| `id` | UUID, primary key | Python (`uuid4`) |
| *the table's own columns* | | |
| `created_at` | timestamptz | Database, on insert |
| `created_by` | UUID, nullable | `BaseService.create` |
| `updated_at` | timestamptz | Database, on every update |
| `updated_by` | UUID, nullable | Every `BaseService` write |
| `deleted_at` | timestamptz, nullable, indexed | `BaseService.soft_delete` |
| `deleted_by` | UUID, nullable | `BaseService.soft_delete` |

A model only declares what is specific to it:

```py title="kernel/tenancy/models/tenant.py"
class Tenant(BaseModel):
    __tablename__ = "tenants"

    name: Mapped[str] = mapped_column(String(255), nullable=False)
```

The building blocks (`UUIDPrimaryKeyMixin`, `TimestampMixin`, `AuditMixin`, `SoftDeleteMixin`) are
exported separately for special tables that need only some of them, such as link tables.

`*_by` columns are plain UUIDs for now. They will reference the users table once the identity feature exists.

## Soft delete

Records are never removed by the API. Delete sets `deleted_at` and `deleted_by`. Then:

- `BaseService.get` and `list` hide deleted records unless `include_deleted=True`.
- `BaseService.restore` brings a record back.
- List endpoints accept `?include_deleted=true`.

## Base service

A feature service only sets its model:

```py title="kernel/tenancy/services/tenant_service.py"
class TenantService(BaseService[Tenant]):
    model = Tenant
```

and inherits:

| Method | Does |
| --- | --- |
| `get(id, include_deleted=False)` | One record or `None` |
| `list(offset, limit, include_deleted=False)` | `(items, total)`, newest first |
| `create(data, actor_id)` | Insert, set `created_by` / `updated_by` |
| `update(obj, data, actor_id)` | Change only the fields that were sent |
| `soft_delete(obj, actor_id)` | Set `deleted_at` / `deleted_by` |
| `restore(obj, actor_id)` | Clear the deleted markers |
| `base_query(include_deleted)` | Override to add a filter to every read |

Services only `flush()`. The `get_db` dependency commits once at the end of the request, or rolls
back on any error, so one request is one transaction.

## Who made the change

`get_actor_id` reads `Authorization: Bearer <token>` and returns the token's `sub` as a UUID, or
`None`. Routers pass it to the service, which stores it in the `*_by` columns.

<Callout type="warn" title="No access control yet">
  `get_actor_id` does not reject anonymous requests. Endpoints are open until the identity and
  access features add authentication and permission checks.
</Callout>

## Migrations

Kernel tables are migrated with Alembic from `kernel/backend`:

```bash
pnpm nx run kernel-backend:migration -- -m "create roles"   # generate from models
pnpm nx run kernel-backend:migrate                          # apply (upgrade head)
```

- A new model is only seen by Alembic once it is imported in `kernel/models.py`.
- Always read a generated migration before committing it.
- On a fresh database you don't run migrations by hand: [first-run setup](/docs/architecture/setup)
  applies them, whether started from the web wizard or with `pnpm nx run kernel-backend:setup -- install ...`.
- With `AUTO_MIGRATE=true`, `api-server` applies kernel migrations on startup.
- Migrations are safe to start from several places at once (API workers, replicas, the CLI). They
  take a Postgres advisory lock, so one runs and the others wait, then find nothing left to do.
