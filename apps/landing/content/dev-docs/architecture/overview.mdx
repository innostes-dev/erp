innostes ERP is built from **two engines** and **plug-ins** that add features to them. The engines contain no business features of their own. Everything a user interacts with, from tenants and users to invoices and departments, comes from a plug-in.

```text
             ┌──────────────────────┐        ┌──────────────────────┐
             │   apps/web-app       │  HTTP  │   apps/api-server    │
             │   UI engine          │ ─────► │   backend engine     │
             │   (React + Vite)     │        │   (FastAPI)          │
             └──────────▲───────────┘        └──────────▲───────────┘
                        │ loads frontend parts          │ loads backend parts
        ┌───────────────┴───────────────┬───────────────┴───────────────┐
        │                               │                               │
 ┌──────┴────────┐               ┌──────┴────────┐               ┌──────┴────────┐
 │ kernel        │               │ module: hrms  │               │ module: crm   │  ...
 │ backend/      │               │ backend/      │               │ backend/      │
 │ frontend/     │               │ frontend/     │               │ frontend/     │
 └───────────────┘               └───────────────┘               └───────────────┘
```

## The engines

| Engine | Folder | Job |
| --- | --- | --- |
| Backend engine | `apps/api-server` | Starts FastAPI, runs database migrations, discovers installed backend plug-ins and mounts their routers, serves `/health` and the OpenAPI specification. See [Building Blocks](/docs/architecture/building-blocks#1-container-view-c4-level-2). |
| UI engine | `apps/web-app` | Mounts the React app shell (sidebar, navigation header, app switcher), enforces setup and authentication gates, and dynamically renders screens registered in module manifests. See [Plug-in Contract](/docs/architecture/plugin-contract#2-frontend-plug-in-contract). |

An engine is plumbing. Any database table, API endpoint, or user interface page belongs inside a plug-in or domain module, never inside an engine.

## Plug-ins and Modules

A plug-in is a self-contained feature package with a backend part and a frontend part:

<Files>
  <Folder name="<plug-in>" defaultOpen>
    <Folder name="backend">
      <File name="pyproject.toml" />
      <Folder name="<python package>" />
      <Folder name="migrations" />
      <Folder name="tests" />
    </Folder>
    <Folder name="frontend">
      <File name="package.json" />
      <Folder name="src" />
    </Folder>
  </Folder>
</Files>

- The **backend** part is a Python package. The backend engine installs it and discovers it automatically via `innostes.modules` entry points.
- The **frontend** part is a pnpm workspace package. The UI engine depends on it and renders its routes and navigation items from its exported manifest.

The **kernel** is the platform foundation plug-in. It provides shared infrastructure (`core`), identity and access management (`auth`, `user`), and multi-tenancy (`tenancy`, `setup`). Domain business modules (`modules/hrms`, `modules/crm`) and platform plugins (`plugins/api-logger`) follow the identical two-part packaging convention.

See [Building Blocks](/docs/architecture/building-blocks) for comprehensive container and engine designs, and [Plug-in Contract](/docs/architecture/plugin-contract) for the strict module integration contract.

<Callout type="info" title="Status">
  The kernel, HRMS, CRM, and API Logger plug-ins are active on both sides. `kernel/backend` is loaded dynamically by `api-server`. `kernel/frontend` and domain module manifests (`@innostes/hrms`, `@innostes/crm`, `@innostes/api-logger`) are registered in `apps/web-app/src/app/catalog.ts` and routed via `AppRouter`.
</Callout>

## Invariant rules

These architectural invariants keep plug-ins completely decoupled:

1. **Engines know nothing about specific plug-ins**: Engines discover plug-ins through entry points and catalog manifests, never importing plug-ins by name.
2. **Plug-ins never import an engine**: Neither `kernel` nor any domain module may import from `apps/api-server` or `apps/web-app`.
3. **Every plug-in may depend on the kernel; the kernel depends on no plug-in**: Dependency flows strictly downward toward `kernel.core`.
4. **Modules do not cross-import internals**: Modules interact through public contracts and database boundaries, never importing private service implementations across packages.
5. **Kernel features follow a strict layer hierarchy**: `core` ← `tenancy` ← `user` ← `auth`. Imports flow only from higher layers to lower layers.

Detailed architectural rules and fitness checks are detailed in [Plug-in Contract](/docs/architecture/plugin-contract#5-architectural-invariants-forbidden-anti-patterns).

## How a request flows

1. `web-app` calls an endpoint (e.g. `POST /tenants`) with the client access token in the `Authorization` header.
2. `CORSMiddleware` validates the browser origin against allowed `CORS_ORIGINS`.
3. `SetupRequiredMiddleware` checks installation status. On uninstalled instances, it returns `503 Service Unavailable` with `setup_required`.
4. `api-server` routes the request to the router mounted by the plug-in.
5. Pydantic schemas validate input; dependency injection provides the transactional database session and authenticated identity.
6. The service layer performs domain validation and flushes changes to PostgreSQL; standard audit mixins populate `created_by` and `updated_by`.
7. The commit completes on successful response delivery, formatted as RFC 7807 Problem Details on failure.

See [Runtime View](/docs/architecture/runtime-view#2-inbound-request-lifecycle-tenant-isolation) for complete sequence diagrams and failure branches.
