`web-app` is the **UI engine**. It provides the app shell, authentication gates, routing, navigation, and renders the dynamic pages that plug-ins (the kernel, business modules, and extensible plugins) provide. Feature pages do not live inside the shell; they are registered dynamically via module manifests. See [Building Blocks](/docs/architecture/building-blocks) and [Plug-in Contract](/docs/architecture/plugin-contract).

On startup, it points the API client at the backend and wraps the application hierarchy in `<SetupGate>` and `<AuthGate>` from `@innostes/kernel`:

```tsx title="src/main.tsx"
import { StrictMode } from 'react';
import * as ReactDOM from 'react-dom/client';
import { Toaster } from '@innostes/ui';
import { AuthGate, configureApi, SetupGate } from '@innostes/kernel';
import App from './app/app';

configureApi({ baseUrl: import.meta.env.VITE_API_URL ?? 'http://localhost:8001' });

const root = ReactDOM.createRoot(document.getElementById('root') as HTMLElement);

root.render(
  <StrictMode>
    <SetupGate>
      <AuthGate>
        <App />
      </AuthGate>
    </SetupGate>
    <Toaster />
  </StrictMode>,
);
```

1. **`SetupGate`**: Queries `GET /setup/status`. If uninstalled, lazy-loads the token-protected setup wizard. Once installed, it renders children.
2. **`AuthGate`**: Verifies the active JWT access token. If missing or expired, it triggers rotating refresh token exchange or presents the login screen.
3. **`AppRouter` & Shell**: Mounts the app shell (`SidebarNav`, `TopHeader`), App Switcher, and dynamically routes to active module and plugin views.

Copy `apps/web-app/.env.example` to `.env` to change the API address (`VITE_API_URL`). The API must allow web-app's address in `CORS_ORIGINS` (default: `http://localhost:4200` and `http://127.0.0.1:4200`).

## Module & Plugin Catalog

The UI engine loads business modules and platform plugins via the dynamic manifest catalogue in `src/app/catalog.ts`:

```ts title="src/app/catalog.ts"
import { apiLoggerManifest } from '@innostes/api-logger';
import { crmManifest } from '@innostes/crm';
import { hrmsManifest } from '@innostes/hrms';

export const BUSINESS_MODULES_CATALOG: CatalogItem[] = [
  hrmsManifest,
  crmManifest,
];

export const PLUGINS_CATALOG: CatalogItem[] = [
  apiLoggerManifest,
];
```

Each manifest declares the module's ID, metadata, routes, sub-features, and visual tokens. The shell reads active module flags from tenant settings to selectively display enabled modules.

## Tasks

The tasks come from `vite.config.mts` (inferred by the Nx Vite plugin):

| Command | What it does |
| --- | --- |
| `pnpm nx serve web-app` | Dev server on http://localhost:4200 |
| `pnpm nx build web-app` | Production build into `apps/web-app/dist` |
| `pnpm nx preview web-app` | Serve the production build on http://localhost:4300 |
| `pnpm nx typecheck web-app` | Type-check TypeScript sources |

## Workspace packages are used from source

`vite.config.mts` adds the `@innostes/source` export condition, so `@innostes/ui`, `@innostes/kernel`, and all module packages are compiled straight from their `src/` folders:

- `serve` and `build` don't build those packages first.
- Edits to the UI library or the module frontends hot-reload in the running app.
- `src/styles.css` has an `@source` line for each package so Tailwind finds their classes.

## Using the design system

Add the package and its styles:

```bash
pnpm add @innostes/ui@workspace:* --filter @innostes/web-app
```

```tsx
import { Button, Card, Dialog } from '@innostes/ui';
```

See [innostes UI installation](/ui/docs/installation) for full documentation.
