`Input` is the primary single-line text entry primitive in `@innostes/ui`. Built on Base UI's input primitive, it automatically coordinates validation states (`aria-invalid`), disabled styling, focus rings, and font metrics across three standardized enterprise size scales.

<ComponentPreview name="forms/input/basic" />

## Import

```tsx
import { Input, SearchInput, PasswordInput, inputVariants } from '@innostes/ui';
```

## When to use

- **Use Input** for brief, single-line textual data such as names, email addresses, phone numbers, codes, or URL slugs.
- **Use Textarea** when users need to enter multiline sentences, remarks, or notes.
- **Use NumberField** when capturing numeric data that requires stepping, bounds checking, or currency formatting.
- **Use InputGroup** when prepending or appending icons, currency symbols, or action buttons directly to the field track.

### Sizes

Inputs support three standardized heights aligning with buttons and selects:

```tsx
<Input size="sm" placeholder="Compact input (32px)" />
<Input size="md" placeholder="Default input (40px)" />
<Input size="lg" placeholder="Comfortable input (48px)" />
```

### Search input

`SearchInput` provides an integrated search glyph, clear button, and accessible keyboard shortcut styling:

```tsx
<SearchInput
  placeholder="Search purchase orders or vendor codes..."
  onClear={() => console.log('Search cleared')}
/>
```

### Password input

`PasswordInput` includes an accessible password visibility toggle button with eye icons:

```tsx
<PasswordInput placeholder="Enter ERP account password" />
```

### File upload input

Inputs with `type="file"` inherit proper custom file-picker button styling:

```tsx
<Input type="file" aria-label="Upload supplier invoice PDF" />
```

### Screen readers and ARIA

- **Accessible naming**: An input must always be associated with a label using `<FieldLabel>`, a native `<label htmlFor="...">`, or an explicit `aria-label`.
- **Validation state**: When wrapped inside `<Field>`, `aria-invalid="true"` is automatically populated upon validation failure, triggering red border rings and auditory error feedback.

## Guidelines

<DoDont>
  <Do>
    Use placeholder text only for formatting examples (e.g. `PO-2026-0001`), never as a replacement for a visible label.
  </Do>
  <Dont>
    Never rely on placeholder text to convey instructions, because placeholders disappear once the user begins typing.
  </Dont>
</DoDont>

<DoDont>
  <Do>
    Set appropriate `type`, `inputMode`, and `autoComplete` attributes (such as `type="email"` or `inputMode="numeric"`).
  </Do>
  <Dont>
    Never disable autocomplete on standard login or address fields unless required by strict security policies.
  </Dont>
</DoDont>
