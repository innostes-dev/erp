`Field` and `Form` provide the foundational scaffolding for all enterprise forms in `@innostes/ui`. Built on Base UI's field primitive, `Field` automatically links labels to controls via `htmlFor`, connects descriptive notes and error messages via `aria-describedby`, and manages `aria-invalid` without manual ID wiring.

## Import

```tsx
import {
  Field,
  FieldLabel,
  FieldDescription,
  FieldError,
  FieldItem,
  Fieldset,
  FieldsetLegend,
  Form,
  FormActions,
  FormGrid,
  FormSection,
} from '@innostes/ui';
```

## When to use

- **Use Field** around any input, select, textarea, or checkbox to automatically manage accessible names, helper text, and validation feedback.
- **Use Form** to coordinate form submission, capture values as keyed objects, map server validation errors, and focus the first invalid control automatically.
- **Use FormGrid and FormSection** to arrange complex ERP forms into structured, responsive multi-column layouts.

### Native constraint validation

`Field` integrates with standard browser HTML5 constraint validation attributes (`required`, `minLength`, `pattern`, `min`, `max`):

```tsx
<Field name="email">
  <FieldLabel required>Work email</FieldLabel>
  <Input type="email" required />
  <FieldError match="valueMissing">Email address is required.</FieldError>
  <FieldError match="typeMismatch">Enter a valid email address.</FieldError>
</Field>
```

### Custom and asynchronous validation

Supply a custom validator function via the `validate` prop on `Field`. The function receives the control value and returns an error message string or `null`:

```tsx
<Field
  name="poNumber"
  validate={async (value) => {
    if (!value) return 'PO number is required';
    const exists = await checkPoExistsOnServer(String(value));
    return exists ? 'This purchase order number already exists.' : null;
  }}
>
  <FieldLabel required>PO number</FieldLabel>
  <Input placeholder="PO-2026-0000" />
  <FieldError match="customError" />
</Field>
```

### Validation timing and focus management

By default, validation runs when the form is submitted (`validationMode="onSubmit"`). You can configure `validationMode` on individual fields or across the entire `Form`:

- `onSubmit`: Validates only upon form submission (avoids premature nagging).
- `onBlur`: Validates when the user tabs out of the input.
- `onChange`: Re-validates immediately on keystroke once the field is dirty.

When a submission fails validation, `Form` automatically moves keyboard focus to the **first invalid field** in DOM order, allowing keyboard and screen-reader users to remediate mistakes immediately.

### Screen readers and ARIA

- **Automatic `aria-describedby`**: `Field` computes unique internal IDs and sets `aria-describedby` pointing to both `<FieldDescription>` and `<FieldError>`.
- **`aria-invalid`**: Automatically set to `true` on the enclosed input whenever validation fails.
- **Live region error announcements**: `<FieldError>` emits errors in an ARIA live region so screen readers announce corrections without requiring navigation away from the current field.

## Guidelines

<DoDont>
  <Do>
    Always wrap interactive form inputs inside a `<Field>` with a visible `<FieldLabel>` for sustained accessibility.
  </Do>
  <Dont>
    Never rely on input `placeholder` text as a substitute for a visible `<FieldLabel>`.
  </Dont>
</DoDont>

<DoDont>
  <Do>
    Write specific, constructive error messages explaining how to resolve the issue (e.g. "Enter an 8-character GSTIN number").
  </Do>
  <Dont>
    Never emit vague errors such as "Invalid input" or "Field error".
  </Dont>
</DoDont>
