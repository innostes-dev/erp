`@innostes/ui` is committed to delivering accessible software for all enterprise operators. Every component in the library is built and tested to conform to the **Web Content Accessibility Guidelines (WCAG) 2.2 Level AA** standard.

Whether an operator at Northwind Traders Pvt Ltd navigates via keyboard shortcuts, relies on screen readers (such as NVDA or VoiceOver), uses voice control, or enables high-contrast display modes, all workflows must remain fully functional and efficient.

## Conformance target

The design system targets **WCAG 2.2 Level AA** across all four principles:

1. **Perceivable**: Text and graphical elements satisfy minimum contrast ratios (≥ 4.5:1 for normal text, ≥ 3.0:1 for large text and UI components). Visual status is never communicated solely through colour.
2. **Operable**: All interactive elements are reachable and operable via standard keyboard sequences. Focus order matches reading order, focus indicators are clearly visible, and modal overlays trap focus securely without keyboard traps.
3. **Understandable**: Controls provide predictable state updates, clear textual error associations via `aria-describedby`, and consistent interaction patterns across forms and dialogs.
4. **Resilient**: Components rely on semantic HTML5 primitives and WAI-ARIA 1.2 specifications, ensuring compatibility across modern browsers and assistive technologies.

## What the library guarantees

When you use `@innostes/ui` primitives, the library automatically handles:

- **Focus trapping and restoration**: Dialogs, sheets, and alert modals trap keyboard focus within the container and restore focus to the triggering element upon dismissal.
- **Roving tabindex**: Multi-item composite widgets (such as `Tabs`, `RadioGroup`, `DropdownMenu`, `TreeView`, and `ToggleGroup`) manage `tabIndex={0}` and `tabIndex={-1}` automatically, enabling direct arrow-key navigation.
- **ARIA attributes and live regions**: Tooltips, progress bars, toasts, and alerts emit proper ARIA roles (`role="alert"`, `role="status"`, `aria-live="polite"`).
- **Verified token contrast**: Base design tokens in `theme.css` and `dark.css` are validated at build time to satisfy WCAG AA contrast minimums.
- **Motion reduction**: Animations automatically disable or simplify when the user enables `prefers-reduced-motion: reduce`.

## What the application team must do

Accessibility is a shared responsibility between the library and the consuming application. Application developers must ensure:

| Developer responsibility | Correct implementation | Why it matters |
| :--- | :--- | :--- |
| **Labels for icon-only buttons** | `<Button size="icon" aria-label="Delete order PO-881">` | Screen readers cannot interpret SVG glyphs without accessible names |
| **Form error linkage** | Use `<Field>` and `<FieldError>` | Associates error text programmatically with inputs via `aria-describedby` |
| **Heading hierarchy** | Use logical `<h1>` to `<h6>` levels | Screen reader users browse pages by jumping across heading structures |
| **Colour redundancy** | Pair warning badges with an icon | Red-green colour-blind operators cannot rely solely on hue shifts |
| **Table column headers** | Provide `<th>` headers with `scope="col"` | Allows screen readers to announce column context when traversing cells |
| **Alternative text** | Provide descriptive `alt` text on images | Screen readers announce image context for visual assets |

## Testing methods

Our quality assurance pipeline tests accessibility through multiple layers of verification:

1. **Automated component audits**: Unit tests run `axe-core` assertions across component render states to detect missing ARIA attributes, orphan labels, or invalid roles before code merges.
2. **Deterministic contrast validation**: A build-time check (`landing:docs-check`) parses all theme tokens and calculates relative luminance to prevent contrast regressions.
3. **Automated browser crawl**: A Playwright crawler audits documentation pages and interactive showcases for focusability, keyboard loops, and landmark semantics.
4. **Manual assistive technology testing**: Regular manual testing verifies auditory announcements and keyboard flows.

## Known issues and continuous hardening

We maintain an active audit tracker (`AUDIT.md`) documenting accessibility improvements:

- **LIB-003**: Customisable internationalisation strings across all ERP widgets (`DataTable`, `TreeView`, `KanbanBoard`) to eliminate hardcoded English text.
- **LIB-004**: Token contrast adjustments across light and dark mode tokens to ensure 100% WCAG AA compliance across all semantic pairings.
- **LIB-007**: Migration from physical directional CSS classes to logical bidirectional properties (`inset-inline-start`, `margin-inline-end`) for full RTL language accessibility.

## Reporting an accessibility problem

If you discover an accessibility barrier or an unannounced state in any `@innostes/ui` component:

1. Open an issue on our repository describing the component, the expected vs actual behaviour, and the assistive technology used (including version numbers).
2. Or contact our accessibility working group directly at `accessibility@innostes.com`.
3. Critical accessibility defects affecting production applications are prioritised as S1 bugs in accordance with our governance policy.
