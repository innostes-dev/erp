`@innostes/ui` adheres to strict architectural conventions across all primitives. Learning these conventions allows developers to predict prop names, event payloads, composition patterns, and styling hooks across the entire design system.

## Composition & exports

All components are exported as flat, named exports from the package entry points. Primitives with multiple child slots (such as `Dialog`, `Select`, or `Tabs`) are imported individually rather than accessed via namespaces:

```tsx
import { Dialog, DialogTrigger, DialogContent, DialogTitle } from '@innostes/ui';
import { MetricCard } from '@innostes/ui/widgets';
import { CartesianCharts } from '@innostes/ui/charts';
```

All exports are fully tree-shakeable: your bundler includes only the code for components your application imports.

## Controlled & uncontrolled state

Every stateful primitive supports both uncontrolled and controlled operation using standard React naming conventions:

| Uncontrolled prop | Controlled prop | Change callback | Event details payload |
| :--- | :--- | :--- | :--- |
| `defaultValue` | `value` | `onValueChange(value, eventDetails)` | `{ reason?: string; event: Event }` |
| `defaultOpen` | `open` | `onOpenChange(open, eventDetails)` | `{ reason?: string; event: Event }` |
| `defaultChecked` | `checked` | `onCheckedChange(checked, eventDetails)` | `{ event: Event }` |
| `defaultPressed` | `pressed` | `onPressedChange(pressed, eventDetails)` | `{ event: Event }` |

### Event details pattern

Callbacks pass the updated value as the first argument, followed by an optional `eventDetails` object indicating the origin trigger (e.g. keyboard escape vs pointer click):

```tsx
<Dialog
  open={isOpen}
  onOpenChange={(nextOpen, details) => {
    if (!nextOpen && details?.reason === 'outside-press') {
      // Prevent closing when user clicks outside modal
      return;
    }
    setIsOpen(nextOpen);
  }}
>
  {/* Modal contents */}
</Dialog>
```

## Polymorphism with the `render` prop

`@innostes/ui` avoids the legacy Radix `asChild` pattern. Instead, primitives built on Base UI utilize the **`render` prop** pattern. This merges accessibility attributes, focus handlers, and class names directly into the custom child element:

```tsx
import Link from 'next/link';
import { Button } from '@innostes/ui';

// Compose an accessible button that renders as a Next.js client link
<Button
  variant="primary"
  nativeButton={false}
  render={<Link href="/orders/PO-2026-0881" />}
>
  View purchase order
</Button>
```

When delegating button rendering to a link element (`<a>`), specify `nativeButton={false}` so the component does not emit an invalid HTML `<button>` inside an anchor.

## Customisation

`@innostes/ui` provides four distinct layers for styling overrides:

### 1. The `className` prop

The `className` prop applies to the component root. Passed classes are merged through `tailwind-merge`, ensuring that user-provided utilities override internal defaults:

```tsx
<Button className="w-full justify-start font-mono">
  PO-2026-0881
</Button>
```

On interactive primitives, `className` can also accept a function receiving the current component state:

```tsx
<Button className={({ disabled }) => (disabled ? 'opacity-40 cursor-not-allowed' : '')}>
  Submit order
</Button>
```

### 2. Multi-part styling with `classNames`

Composite widgets and complex data display components provide a `classNames` prop accepting a map of slot names to utility strings:

```tsx
<MetricCard
  label="Total Procurement"
  value="₹1,45,280.00"
  classNames={{
    root: 'border-blue-500/30 bg-blue-50/10',
    label: 'text-blue-700 dark:text-blue-400 font-semibold',
    value: 'font-mono text-2xl tracking-tight',
  }}
/>
```

### 3. The `data-slot` attribute

Every internal element emits a deterministic `data-slot` attribute (e.g. `data-slot="dialog-content"`, `data-slot="card-header"`). You can target child slots from parent stylesheets or container selectors:

```css
/* Customise all metric card values inside a financial summary section */
.finance-overview [data-slot="metric-card-value"] {
  font-family: var(--font-mono);
  color: var(--color-emerald-700);
}
```

### 4. Interactive state attributes

Primitives expose interactive state via HTML `data-*` attributes (`data-state="open"`, `data-checked`, `data-disabled`, `data-highlighted`, `data-invalid`). You can style these states using Tailwind CSS variants:

```tsx
<div className="border-border data-invalid:border-destructive data-invalid:ring-destructive">
  {/* Field contents */}
</div>
```

### 5. Server-safe variant helpers

Every styled component exports its underlying class-variance-authority helper function (e.g. `buttonVariants()`, `badgeVariants()`, `inputVariants()`). These functions are pure JavaScript and execute safely on the server:

```tsx
import { buttonVariants } from '@innostes/ui';

// Generate button styles for standard HTML or external router links
const linkClasses = buttonVariants({ variant: 'outline', size: 'sm' });
```

## Ref forwarding

Every component wraps its DOM root in React's `forwardRef`. Refs point directly to native DOM elements (`HTMLButtonElement`, `HTMLDivElement`, `HTMLInputElement`), allowing direct integration with form management libraries (such as React Hook Form) across React 17, React 18, and React 19.

## Server Components & client boundaries

- **Interactive components** declare `'use client'` at their file headers. You can import them directly into Server Components in Next.js App Router without manual wrappers.
- **Pure helpers** (`cn()`, `formatDate()`, `buttonVariants()`, `badgeVariants()`) do not import browser-specific APIs and execute on both client and server.

## Standard size scale

Interactive controls share a unified size scale so adjacent controls align in toolbars and data tables:

| Size | Height | Recommended application |
| :--- | :--- | :--- |
| `sm` | 32px | High-density audit grids, compact filter bars, table pagination |
| `md` | 40px | Standard forms, default modal actions, primary toolbars |
| `lg` | 48px | Mobile ERP terminals, high-consequence confirmation dialogs |

## Internationalisation & RTL support

All customer-facing text is customizable to support enterprise multi-language requirements. Rather than hardcoding English strings, components expose override props:

- `closeLabel`: Dialog, Alert, Sheet dismissal labels (defaults to `"Close"`).
- `labels`: Component-specific string maps (e.g. `labels={{ previousPage: 'Previous', nextPage: 'Next' }}` on `Pagination`).
- **Logical CSS properties**: Styles use CSS logical properties (`margin-inline-end`, `inset-inline-start`, `border-inline-start`) instead of physical directions (`left`, `right`, `mr-`, `ml-`). Wrap the application in `<DirectionProvider direction="rtl">` for Arabic, Hebrew, or Urdu localization.
